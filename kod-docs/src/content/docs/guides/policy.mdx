A `Policy` says what the agent is allowed to do, project by project. It is read from `.kod/policy.toml` in the project root, merged over a preset, and consulted by the engine **before every tool call**. The decision replaces ad-hoc flags and scattered permission bitmasks: one engine, one decision point, one log entry per call.

## Four layers, later overriding earlier

1. **Preset** — `read-only`, `standard`, or `yolo`. The default preset is `standard`.
2. **Global config** — the `[tools]` section of `~/.config/kod/config.toml`. Today this carries `confirm_writes`, which maps to `standard` (true) or `yolo` (false) for backward compatibility.
3. **Project policy** — `.kod/policy.toml`, committed to the repo like an `.editorconfig`.
4. **CLI override** — `--preset yolo` on the command line.

Within a layer, `[tools.<name>]` entries give a per-tool decision (`allow` / `deny` / `ask`) plus optional path globs and command allowlists. A `deny` always wins over an `allow` at glob-conflict time — the same rule `ToolContext::is_path_allowed` applies.

## The three presets

| Preset | Reads | Writes / shell | Use it for |
| --- | --- | --- | --- |
| `read-only` | allowed | **denied without asking** | unattended runs, code review, auditing |
| `standard` *(default)* | allowed | **require approval** | everyday interactive work |
| `yolo` | allowed | **allowed without prompting** | trusted throwaway sandboxes |

`standard` matches the historical behaviour of `tools.confirm_writes = true`: writes and shell commands pause for an approval dialog (TUI: `y`/`n`/Esc) or a stdin prompt (CLI). `read-only` is the right default for any unattended script — a script cannot answer an approval prompt, so asking would be a lie. `yolo` is the pre-PolicyEngine behaviour of `confirm_writes = false`, kept under an honest name.

## Writing a `.kod/policy.toml`

```toml
# .kod/policy.toml — committed to the repo
preset = "standard"

[tools.write_file]
mode = "ask"
paths    = ["src/**", "docs/**"]
forbidden = ["**/.env", "**/*.pem"]

[tools.execute_command]
mode = "ask"
binaries           = ["cargo", "rustfmt", "git"]
forbidden_binaries = ["curl", "rm"]

[tools.web_fetch]
mode    = "allow"
network = true
domains = ["docs.rs", "crates.io"]

[git]
history_protected = true   # .git is mounted read-only at the sandbox
```

Field reference:

- `mode` — overrides the preset's decision for this tool: `allow`, `deny`, or `ask`.
- `paths` — allow-list of path globs; a path matching none of them is denied.
- `forbidden` — forbidden path globs; deny wins over allow.
- `binaries` / `forbidden_binaries` — command allow/deny lists, meaningful for `execute_command`; a command whose first token is not allow-listed is denied. This is convenience, never a security guarantee — the sandbox is.
- `network` — per-tool override of the global `llm.network_access`.
- `domains` — domain allow-list for `web_fetch` when network is enabled.
- `git.history_protected` — mounts `.git` read-only at the sandbox (default true).

## Glob semantics

Path globs follow gitignore intuition, implemented with `globset` and `literal_separator(true)`: `*` does not cross `/`, `**` does. A pattern is tried three ways — verbatim (for absolute patterns), relative to the working directory (the usual project-relative form like `src/**`), and, unless the pattern is anchored, prefixed with `**/` so `src/**` also matches files under nested directories the way a shell glob would.

<Aside type="caution">
  Command allowlists are a footgun if treated as security. `binaries = ["bash"]` allows bash to run anything. They are ergonomics for steering the agent; the actual containment comes from [Sandboxing](/guides/sandboxing/).
</Aside>

## Every decision is logged

`PolicyEngine::decide` is pure with respect to the tool call: it takes the tool name, the JSON arguments, and the effective `ToolContext` (whose `working_dir` anchors relative paths), and returns a `PolicyDecision { outcome, rule, source }`. The engine logs this as a `SessionEntry::PolicyDecision` and then runs, refuses, or asks. That means the JSONL session log answers *why* a call was allowed or refused, not just *what* happened — replay it, read it, or diff it.
