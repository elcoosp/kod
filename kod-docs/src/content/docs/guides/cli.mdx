The CLI is the scriptable half of KOD. It exposes the same engine as the TUI — the same policy engine, memory, skills, and session logging — through one-shot commands that compose well with pipes, cron jobs, and shell scripts. Where the TUI optimises for long interactive sessions, the CLI optimises for *repeatable* ones.

The full command surface is documented at [CLI Commands](/reference/cli/). This page is the practical tour.

## The shape of the binary

```
kod [--verbose] <COMMAND>
```

Commands fall into five rough groups:

- **Sessions** — `chat` (plain REPL), `tui` (full interface), `agent` (one-shot goal), `prompt` / `run` (single prompt), `swarm` (multi-agent), `serve` (daemon).
- **Model management** — `models`, `profile`, `theme`, and the `[llm]` parts of `config`.
- **Inspection** — `skills`, `sessions`, `memory`, `map`, `doctor`, `config`, `tools`, `policy`, `sandbox`.
- **Audit and repair** — `replay`, `checkpoint`.
- **Setup** — `init`, `test`, `completions`, `update`.

Bare `kod` prints a short onboarding summary: the four entry points, where your config lives, and which skill directories were found.

## The four ways to send a prompt

**`kod chat`** starts a plain REPL with streaming output — the lightest way to interact with the model. No tool rows, no panel, just the conversation. Useful flags: `--model` to override the model for this session, `--system-prompt` to replace the built-in one, `--sandbox` to route shell commands through the platform sandbox, and `--preset` to override the policy for the session.

**`kod prompt "<text>"`** answers one prompt and exits — no banner, no REPL. The reply goes to stdout and diagnostics go to stderr, so it pipes cleanly. `-` reads the prompt from stdin. It is the command you want inside shell pipelines:

```bash
kod prompt "summarise the TODO comments in src/ in a bullet list"
git diff main..feature | kod prompt -   # read the prompt from stdin
```

**`kod run "<text>"`** is `prompt` in streaming form: the reply prints to stdout as it is generated instead of at the end. Same `-` stdin convention, same clean output.

**`kod agent -g "<goal>"`** runs a single agent against a goal — the full loop with tool calls — and exits when done. This is the workhorse for automation:

```bash
kod agent -g "add a doc comment to every public function in src/lib.rs"
kod agent -n reviewer -g "summarise the changes in the last commit" --preset read-only
```

<Aside type="caution">
  <code>kod agent</code> has no interactive consumer. When the policy says a write needs approval, the run refuses the write with an explanatory message rather than waiting — an unattended process cannot click <em>yes</em>. For scripts, either pass <code>--preset read-only</code>, accept the refusals by design, or use <code>--preset yolo</code> only where you truly mean it.
</Aside>

## The daemon: `kod serve`

Starting an engine per one-shot prompt costs process startup and engine init. `kod serve` starts a long-lived engine behind a Unix socket; `kod prompt --remote` sends prompts to it instead of building an in-process engine:

```bash
kod serve &                        # daemon, listening on the default socket
kod prompt --remote "lint-check my last commit message"
kod serve --stop                   # ask the daemon to exit
```

The socket lives at `$XDG_RUNTIME_DIR/kod.sock` (Linux) or `~/.kod/run/kod.sock` (macOS); `--socket <path>` overrides it. It is Unix-socket only, never TCP — there is no network surface.

## Inspecting the world

`kod skills` lists the merged skill set from every standard directory (or `--json` for scripts). `kod map` prints the repository map the engine uses for grounding — handy for sanity-checking what the agent can see (`--max-chars` caps the output, default 16000). `kod models` lists what the configured provider offers, with `--filter` to narrow. `kod tools list` prints the tool registry the model sees, `kod tools show write_file` one tool's schema, and `kod policy show` the effective permissions. `kod doctor` runs the diagnostics suite: config, endpoint, skills, memory, sandbox, git.

`kod config` is a small toolbox in itself:

## Auditing: replay and checkpoints

Two commands make KOD's audit story concrete:

```bash
# re-run every tool call from a past session — without the model
kod replay ~/.kod/sessions/1730000000000.jsonl --execute

# list file-level checkpoints, inspect one, restore it
kod checkpoint list
kod checkpoint diff <id>
kod checkpoint restore <id>
```

`replay` is the regression check: any recorded session can be re-executed against the codebase at any later commit to see whether the same operations still make sense (or still pass). Without `--execute`, it prints what would run. `checkpoint` is the undo: KOD snapshots every file before a mutating tool call touches it, so `write_file` and `patch_file` damage is always recoverable — and `checkpoint diff` shows you exactly what restoring would change.

<Aside type="caution">
  <code>--execute</code> performs real writes and commands against your working tree. Review a session with plain <code>kod replay &lt;file&gt;</code> first when you are not sure what it contains.
</Aside>

## Recipes

A few patterns that work well in practice:

<Tabs>
<TabItem label="Nightly audit">
  ```bash
  # classify recent changes, read-only, no writes possible
  kod agent --preset read-only \
    -g "review yesterday's commits and flag risky patterns" \
    | tee "$HOME/logs/kod-audit-$(date +%F).txt"
  ```
</TabItem>
<TabItem label="Explain a diff in CI">
  ```bash
  git diff origin/main..HEAD | kod prompt - > /tmp/pr-summary.txt
  ```
</TabItem>
<TabItem label="Long-running daemon for scripts">
  ```bash
  kod serve &
  for f in $(git diff --name-only); do
    kod prompt --remote "review $f for obvious bugs" >> review.md
  done
  kod serve --stop
  ```
</TabItem>
<TabItem label="Skill CI gate">
  ```bash
  # machine-readable skill inventory + validation for CI
  kod skills --json
  kod validate-skills
  ```
</TabItem>
</Tabs>

<Aside type="tip">
  <code>--preset read-only</code> is the right default for any unattended run. It denies <code>write_file</code>, <code>patch_file</code>, and <code>execute_command</code> outright rather than asking — an unattended script cannot answer an approval prompt anyway.
</Aside>
