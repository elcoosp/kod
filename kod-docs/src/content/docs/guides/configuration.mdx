KOD reads its configuration from a single TOML file, auto-generated on first run, with sane defaults for every key. You can go from zero config to a working session without touching anything — the config exists so you can *stop* accepting defaults, not so you have to set them.

## Where the file lives

- **Linux:** `~/.config/kod/config.toml`
- **macOS:** `~/Library/Application Support/kod/config.toml`

`kod config path` prints the exact location; `kod config edit` opens it in `$EDITOR`; `kod config validate` parses it and exits non-zero when it is invalid — useful in CI or after a hand-edit. Corrupt files are not fatal: KOD warns and falls back to defaults instead of exiting, so a bad edit never bricks your session.

## The shape of the file

A config only needs the blocks you care about — every omitted section fills from defaults. The example below is a realistic *complete* file:

```toml
# ── Models ─────────────────────────────────────────────────────
[llm]
network_access = false          # opt-in network access for web_fetch

[[llm.endpoints]]               # one block per model server
name         = "local"
provider     = "openai-compatible"   # or "anthropic" (declared, not implemented yet)
base_url     = "http://localhost:11434/v1"
model        = "qwen2.5-coder:7b"
context_window = 32768
# api_key_env = "MY_API_KEY"    # env var NAME holding the key — never the key itself
# temperature = 0.7
# max_tokens  = 4096
# timeout_secs = 300
# [llm.endpoints.pricing]       # USD per million tokens, for TUI cost display
# input_per_mtok_usd = 0.15
# output_per_mtok_usd = 0.60

# ── Memory ─────────────────────────────────────────────────────
[memory]
short_term_capacity = 100
scope               = "global"  # or "project" → <cwd>/.kod/memory.redb
# extract_on_shutdown = false   # one LLM pass to save durable facts at exit

# ── Skills ─────────────────────────────────────────────────────
[skills]
enable_hot_reload     = true
max_skills_per_query  = 3
match_threshold       = 0.7
# skills_dir = "/custom/skills" # overrides the standard search paths

# ── Swarms ─────────────────────────────────────────────────────
[swarm]
max_agents         = 5          # clamped to 2–8 by the runner
merge_results      = true
agent_timeout_secs = 300        # per-agent wall clock; 0 disables
agent_retries      = 1

# ── Write follow-ups ───────────────────────────────────────────
[tools]
auto_check = false              # run compiler/linter after writes (cargo, tsc, ruff, go vet)
auto_lsp   = true               # run language-server diagnostics after writes

# ── Hooks ──────────────────────────────────────────────────────
[hooks]
enabled = false
# pre_tool_use  = { write_file = "rustfmt {path}" }
# post_tool_use = { write_file = "cargo check" }

# ── MCP servers (optional) ─────────────────────────────────────
# [mcp.servers.filesystem]
# command = "npx"
# args = ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
# enabled = true
# call_timeout_secs = 60
# [mcp.servers.filesystem.env]
# LOG_LEVEL = "info"

# ── Custom slash commands (optional) ───────────────────────────
# [commands]
# review = "Review the last change in {cwd} and point out risks."
# explain = "Explain what this code does:\n\n{args}"
```

## Endpoints instead of a single model

The `[llm]` section holds a **list of named endpoints**, not one flat model. The first endpoint is the default; everything that affects the wire — `base_url`, `model`, `temperature`, `max_tokens` — lives on the endpoint. That is what lets you point different work at different servers:

```toml
[llm.routing]
by_task  = { Debugging = "cloud", Simple = "local" }
fallback = ["local", "cloud"]     # try in order when the primary fails
swarm    = { Planning = "cloud", Coding = "local" }
```

- `by_task` maps a [task type](/concepts/router/) (`Simple`, `Debugging`, …) to an endpoint name.
- `fallback` is the ordered retry chain for retryable errors.
- `swarm` maps swarm capabilities (`Planning`, `Coding`, …) to endpoints, so a swarm can think with one model and code with another.

Names that do not match a defined endpoint are dropped with a warning at load time — a typo cannot silently disable a route.

## API keys live in the environment

Endpoint blocks never contain key material — only the *name* of the environment variable that holds it:

```toml
[[llm.endpoints]]
name        = "openai"
provider    = "openai-compatible"
base_url    = "https://api.openai.com/v1"
model       = "gpt-4o-mini"
api_key_env = "OPENAI_API_KEY"
```

A shared or committed config therefore cannot leak a secret. The memory section has the same pattern for the optional embedding API (`memory.embedding_api_key_env`).

## Out-of-range values are clamped, not fatal

At load time every endpoint is validated: temperature is clamped to 0.0–2.0, `context_window` has a coherent floor (2000), `max_tokens = 0` falls back to the default, timeouts are floored at 1s, and empty `base_url`/`model` values are replaced. Each adjustment logs a warning naming the endpoint and the corrected value. The philosophy: be forgiving at load, loud about it, and precise once running.

## Per-project overrides: `.kod/`

Three things can be scoped to a project directory instead of your home directory:

1. **Policy** — `.kod/policy.toml` in the project root is committed to the repo like an `.editorconfig` and layers over your global config. See [Policy & Permissions](/guides/policy/).
2. **Memory** — `memory.scope = "project"` puts the long-term database under `<cwd>/.kod/memory.redb` instead of `~/.kod/data/kod.redb`, giving each project its own memory.
3. **Keybindings** — a `.kod-keys.toml` in the project remaps TUI keys for that repo only. See [TUI Keybindings](/reference/tui-keys/#rebinding-keys).

## Custom slash commands

The `[commands]` block registers your own TUI slash commands. Each key becomes `/key`, and its value is the prompt that gets sent:

```toml
[commands]
review  = "Review the last change in {cwd} and point out risks."
explain = "Explain what this code does:\n\n{args}"
```

`{args}` is replaced by everything typed after the command name; `{cwd}` by the current working directory. `/review` needs no arguments; `/explain foo.bar` sends the template with `foo.bar` substituted in.

## Inspecting what actually applies

Because configuration comes from defaults plus your edits, the useful question is often “what is *effective*?” rather than “what did I write?”:

<Tabs>
<TabItem label="Effective config">
  ```bash
  kod config show-merged   # defaults merged with user config, reproducible
  ```
</TabItem>
<TabItem label="Raw file">
  ```bash
  kod config show-raw      # verbatim file contents, comments included
  ```
</TabItem>
<TabItem label="Just the LLM block">
  ```bash
  kod profile show         # the effective [llm] section
  ```
</TabItem>
</Tabs>

`kod config export [path]` dumps the effective config to a file (or stdout with `-`; refuses to overwrite without `--force`), which gives you a fully self-documenting starting point.

<Aside type="tip">
  Piping <code>kod config show-merged</code> into a file and committing it is a clean way to version your baseline and diff future changes against it.
</Aside>
