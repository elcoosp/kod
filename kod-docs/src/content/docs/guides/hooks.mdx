Hooks let you run your own shell commands at two points in the tool lifecycle: **before** a tool executes (`pre_tool_use`) and **after** it completes (`post_tool_use`). They are driven entirely by config templates — no scripting language to learn, no plugin API to import — which keeps them auditable like everything else in KOD: a hook is a line in your `config.toml`.

## Enabling hooks

```toml
[hooks]
enabled = false
# pre_tool_use  = { write_file = "rustfmt {path}" }
# post_tool_use = { write_file = "cargo check" }
```

Hooks are disabled by default. Flipping `enabled = true` activates both maps. Each entry keys a **tool name** (`write_file`, `patch_file`, `execute_command`, …) to a **shell command template**, and `{path}`-style placeholders are substituted with the tool call's arguments before execution.

## What they are good for

The canonical pair from the config comments shows the intended shape:

- **`pre_tool_use` on `write_file`: `rustfmt {path}`** — every file the agent writes gets formatted the moment it lands, so style is enforced at the source rather than reviewed at the end.
- **`post_tool_use` on `write_file`: `cargo check`** — every write is immediately followed by a compile check, so a broken edit surfaces in the same round that produced it instead of five prompts later.

The same pattern extends naturally: run `eslint --fix` after JavaScript edits, `gofmt` after Go writes, or a quick test suite after any `patch_file` on a crate you care about.

<Aside type="tip">
  If all you want is post-write diagnostics, check whether the built-in switches do it first: <code>tools.auto_lsp = true</code> (default) appends language-server diagnostics after writes, and <code>tools.auto_check = true</code> runs the project compiler/linter with baseline-aware output. Hooks are for commands that are *yours* — formatters with house rules, notification bells, snapshot scripts.
</Aside>

## How hooks relate to policy

Hooks execute *inside* the tool lifecycle, not in place of it. The order per call is:

1. Policy decision (preset → global → project → CLI) — allow, deny, or ask.
2. If allowed: `pre_tool_use` hook for this tool, if one is configured.
3. The tool executes (sandboxed if requested, path-locked, checkpointed if mutating).
4. `post_tool_use` hook, if configured.

A denied tool call never reaches its hooks — there is nothing to hook around. Hook commands are themselves shell commands, so treat them with the same care as policy allowlists: they run with your permissions, outside the tool sandbox.

<Aside type="caution">
  Keep hooks fast. A <code>post_tool_use</code> hook runs after every matching tool call — a hook that takes 30 seconds turns every write into a 30-second round. <code>cargo check</code> is a good hook; <code>cargo test</code> usually is not.
</Aside>

## Where hooks live in the engine

The hook system lives in `kod-core` alongside the session log. Hook commands run in your session's shell with your privileges; their output is not injected into the model's prompt — if you want the model to *see* the result of a check, that is precisely what `tools.auto_check` and the `check` tool are for (see [Tools](/guides/tools/#write-follow-ups-lsp-and-check)).
