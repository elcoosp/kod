Tools are how the agent touches your system. KOD ships 24 built-in tools, and every single call passes through the same gauntlet: the [policy engine](/guides/policy/) decides allow/deny/ask, the executor enforces a timeout, a per-path advisory lock table prevents concurrent writes to the same file, and `--sandbox` can route shell commands through the platform sandbox. `kod tools list` prints the registry exactly as the model sees it; `kod tools show <name>` prints one tool's schema.

## The tool families

**File system** — `read_file`, `write_file`, `patch_file`, `list_files`, `grep`, `file_info`, `search_files`. The write paths are careful: `write_file` results attach a unified diff of what changed, and both `write_file` and `patch_file` snapshot the target file first so [checkpoints](/guides/sessions/#checkpoints-file-level-undo) can restore it. `search_files` finds files by name pattern when `grep`'s content search is the wrong shape.

**Git** — `git_status`, `git_diff`, `git_commit`, `git_branch`. Status and diff are read-only; commit and branch-create are write-gated like any other mutating tool. Together they let the agent reason about your working tree and — when policy allows — commit its own work on a branch without shelling out.

**Shell** — `execute_command`, the most powerful and the most gated tool. It is the one most affected by policy presets (denied outright under `read-only`), command allowlists (`binaries` / `forbidden_binaries` in `.kod/policy.toml`), and sandboxing.

**Project checks** — `check` runs the compiler or linter that matches your project — Cargo, `tsc`, `ruff`, or `go vet` — and returns structured diagnostics. The agent uses it to ask "did that edit break the build?" without grepping compiler output.

**Planning and interaction** — `todo` maintains a visible task list for multi-step work, and `ask_user` lets the agent stop and ask *you* a question instead of guessing.

**Memory** — `memory_save` and `memory_search` give the model direct access to the long-term store. Registered only when memory is enabled; see [Memory](/guides/memory/).

**Swarm** — `swarm_note` and `swarm_read`, a shared blackboard that concurrent agents use to publish and read each other's findings; see [Agent Swarms](/guides/swarm/).

**Web** — `web_fetch`, an HTTP/HTTPS fetch with SSRF protection: loopback, private, link-local, and metadata endpoints are refused. It is the only tool that can reach the network, and only when `llm.network_access` (or the tool's own `network` policy) enables it.

**LSP** — `lsp_diagnostics`, `lsp_definition`, `lsp_references`, `lsp_hover`. When a language server for the file's language is on your `PATH`, these give the agent compiler-grade answers — otherwise they fail with a message naming the missing server. See below.

## Permission gating in one paragraph

There is no ungated path. The `Tool` trait's execution context (`ToolContext`) carries permissions and anchors relative paths to a working directory; the policy engine consults the effective policy — preset, global config, project `.kod/policy.toml`, CLI override — before every call, and the decision (including which rule and which layer decided) is logged to the session. A `deny` always wins over an `allow` at glob-conflict time, and path globs follow gitignore semantics: `*` does not cross `/`, `**` does.

## Concurrency safety

A per-path advisory lock table means two agents (say, in a [swarm](/guides/swarm/)) cannot silently interleave writes to the same file. Conflicts are detected and surfaced rather than last-write-wins. This is what makes the swarm's shared-workspace mode usable instead of terrifying.

## Which tool when

| You want the agent to… | Tool that runs | Typical policy |
| --- | --- | --- |
| Inspect code, find patterns | `read_file`, `list_files`, `grep`, `file_info`, `search_files` | allowed everywhere |
| Edit a file | `write_file` / `patch_file` | `ask` under `standard` |
| Understand recent changes | `git_status`, `git_diff` | allowed |
| Commit work / create a branch | `git_commit`, `git_branch` | `ask` under `standard` |
| Run tests, build, format | `execute_command` | `ask` under `standard` |
| Verify the build after an edit | `check` | allowed (read-only by nature) |
| Look something up online | `web_fetch` | needs network access enabled |
| Save a fact for later | `memory_save` / `memory_search` | allowed when memory is on |

## Write follow-ups: LSP and check

Two config switches add automatic verification after every successful write:

```toml
[tools]
auto_lsp   = true    # default — cheap, sub-second per file
auto_check = false   # opt-in — runs the compiler, which is not free
```

- **`auto_lsp`** runs the language server's diagnostics pass on the touched files and appends a `## LSP diagnostics` block to the next turn's prompt. It only runs for languages that have a server on `PATH`; a session with none installed simply sees no block. The same capability is available to the agent on demand via `lsp_diagnostics`, `lsp_definition`, `lsp_references`, and `lsp_hover`.
- **`auto_check`** runs the project check (`cargo`, `tsc`, `ruff`, `go vet`) and appends its diagnostics the same way. A baseline is captured at startup, so the model is shown *its* errors, not pre-existing ones. On a large workspace this adds a compiler run per write — that is why it defaults to off. The TUI's `/check` runs the same check on demand.

<Aside type="note">
  Where a language server is missing, the LSP tools do not silently return nothing — they error with a message naming the missing binary, and the model can tell you what to install.
</Aside>
