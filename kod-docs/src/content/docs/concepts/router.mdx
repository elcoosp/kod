The Task Router is the first thing your prompt meets. `TaskRouter::classify_task` reads the input and assigns it a `TaskType`, and that classification quietly shapes the whole round: which skills are matched, how the grounded prompt is framed, and how the engine treats the result. It is keyword- and pattern-based — deterministic, fast, and inspectable — not a model call, which means classification costs nothing and never varies between runs of the same prompt.

## The task types

| `TaskType` | What it covers |
| --- | --- |
| `Simple` | Questions, explanations, lookups — no code changes implied |
| `CodeModification` | Edits to existing code — refactors, doc comments, tweaks |
| `Debugging` | Failures, errors, misbehaviour to diagnose |
| `Research` | Exploration and understanding across many files |
| `Testing` | Writing or fixing tests |
| `Documentation` | Docs and comments as the primary output |
| `Complex` | Tasks that combine several of the above |
| `MultiStep` | Long-horizon tasks needing ordered operations |

## How classification affects the round

Two concrete effects worth knowing:

1. **Skill matching budget.** The router configures how many skills ride along per prompt (`max_skills_per_query`, default 3). Classification and matching work together: a `Debugging` prompt and a `Documentation` prompt can surface different skill sets from the same directory.
2. **Prompt shaping.** The grounded prompt reflects the task type, so the model starts from a framing that fits the request instead of inferring one from scratch.

## Configuration

The router's `RouterConfig` carries the knobs that shape a round:

- `enable_memory` — whether memory participates in grounding (the test suite turns this off for in-process tests to avoid DB contention).
- `max_skills_per_query` — the per-prompt skill cap.
- `working_dir` — the anchor for all relative paths in tool calls and globs.
- `context_window` — read from `llm.context_window`; sizes the memory manager's per-prompt budget so long sessions do not drop entries that a large model could have kept.
- `short_term_capacity` — read from `memory.short_term_capacity`; defaults to 100 when built directly.

## Precision is pinned by tests

Classification is string surgery, and string surgery is where subtle bugs live — so the matcher gets dedicated coverage. The changelog records multiple substring-matcher and word-boundary fixes in `TaskRouter::classify_task`, and the router's test suite pins the classification of realistic prompts. When you suspect a misclassification, the fastest check is the same one the tests use: classify the prompt and see which type falls out.

<Aside type="caution">
  One deliberate change: the router used to carry placeholder handlers that returned fabricated text when no provider was configured. They were removed — `Engine::process()` without a provider now returns an `InvalidState` error instead of inventing an answer. Fail loudly beats fake politely.
</Aside>
