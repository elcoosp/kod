The Task Router is the first thing your prompt meets. The router reads the input and assigns it a `TaskType`, and that classification quietly shapes the whole round: which skills are matched, how the grounded prompt is framed, and how the engine treats the result. It is keyword- and pattern-based — deterministic, fast, and inspectable — not a model call, which means classification costs nothing and never varies between runs of the same prompt.

## The task types

| `TaskType` | What it covers |
| --- | --- |
| `Simple` | Questions, explanations, lookups — no code changes implied |
| `CodeModification` | Edits to existing code — refactors, doc comments, tweaks |
| `Debugging` | Failures, errors, misbehaviour to diagnose |
| `Research` | Exploration and understanding across many files |
| `Testing` | Writing or fixing tests |
| `Documentation` | Docs and comments as the primary output |
| `Complex` | Tasks that combine several of the above |
| `MultiStep` | Long-horizon tasks needing ordered operations |

## How classification affects the round

Two concrete effects worth knowing:

1. **Skill matching.** The router decides which skills ride along per prompt, up to `max_skills_per_query` (default 3) with a match threshold of `0.7`. A `Debugging` prompt and a `Documentation` prompt can surface different skill sets from the same directory.
2. **Prompt shaping.** The grounded prompt reflects the task type, so the model starts from a framing that fits the request instead of inferring one from scratch.

Classification also feeds [multi-model routing](/guides/configuration/#endpoints-instead-of-a-single-model): with `[llm.routing].by_task`, you can send `Debugging` work to a stronger endpoint while `Simple` questions stay on the fast local model.

## What the router considers

The router config carries the knobs that shape a round:

- `enable_memory` — whether memory participates in grounding.
- `max_skills_per_query` — the per-prompt skill cap.
- `working_dir` — the anchor for all relative paths in tool calls and globs.
- `context_window` — read from the endpoint; sizes the memory manager's per-prompt budget so long sessions do not drop entries that a large model could have kept.
- `short_term_capacity` — read from `memory.short_term_capacity`.

## When routing surprises you

Because classification is deterministic string matching, a surprising result is always traceable:

- `kod chat --verbose` (or the TUI's expanded tool rows) shows the classification for each round.
- The header in the TUI shows the task type as the round starts — `CodeModification`, `Debugging`, and so on.
- If a prompt is classified differently from what you intend, rephrase with the verbs the router keys on ("refactor", "debug", "explain", "write tests", "document") — or let `/goal` set a standing framing for the whole session.

<Aside type="caution">
  One deliberate design choice: the router used to return fabricated placeholder text when no provider was configured. It does not any more — a missing provider produces an explicit error instead of an invented answer. Fail loudly beats fake politely.
</Aside>
