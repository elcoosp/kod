## Audit findings: sandbox backends (0 changes, all candidates refuted)

Audited `crates/kod-tools/src/context.rs` (`SandboxResolver`,
`bwrap_invocation`, `seatbelt_invocation`) and
`crates/kod-tools/src/sandbox/landlock.rs` (697 lines) with the
same guard-shape method. Six guards scanned, three candidates
surfaced, all three refuted by reading the code:

### R1 — bwrap `--` argument terminator — SAFE

`bwrap_invocation` (context.rs:406-469) ends with:

```
args.push("--die-with-parent".into());
args.push("--".into());
```

`execute_command` then does `c.args(&inv.args)` followed by
`.arg(shell).arg(shell_flag).arg(command)`, so the full argv ends
`... --die-with-parent -- sh -c <command>`. bwrap treats everything
after `--` as the command, not as a bwrap flag — a crafted command
string like `--bind / /` is passed to sh, not re-parsed by bwrap.

Two tests pin the shape (`context.rs:1567`, `:1603`:
`assert_eq!(inv.args.last(), Some("--"))`).

### R2 — bwrap network isolation — SAFE

context.rs:458-460:

```
if opts.net_deny {
    args.push("--unshare-net".into());
}
```

Both backends handle `net_deny`: bwrap via `--unshare-net`,
landlock at `sandbox/landlock.rs:251-277` which refuses below
ABI 4 (`if profile.net_deny && abi < 4 { return Err(...) }`)
rather than silently shipping an unprotected sandbox. Test at
`landlock.rs:672`.

### R3 — landlock RO/RW rule construction — SAFE

`LandlockProfile` (`landlock.rs`) has distinct fields:

```
pub ro_paths: Vec<PathBuf>,
pub rw_paths: Vec<PathBuf>,
```

The read-only mask is `LANDLOCK_ACCESS_FS_EXECUTE |
LANDLOCK_ACCESS_FS_READ_FILE | LANDLOCK_ACCESS_FS_READ_DIR`
(no WRITE_FILE, no MAKE_*); the full handled mask at
`handled_access_fs` adds WRITE_FILE and the MAKE_* variants for
`rw_paths`. The masks are constructed from path class, not from
a shared default.

Additionally, `claims_git_readonly` is checked in `apply`: since
landlock rules are additive, a `.git` ro-rule under a blanket
worktree rw-rule would be a silent no-op, and `apply` refuses
that configuration rather than degrading to unprotected.

### Other guards checked and clean

- **Guard 1** — every `Command::new` in `kod-tools/src` routes
  through `context.sandbox` / `sandbox_invocation`:
  `tools.rs:1136` (execute_command, through `inv.program`),
  `check.rs:424` (project compiler, through the sandboxed shell),
  `git.rs` (git subprocesses via `run_git`, through the same
  resolver), `relevance.rs:117` (rg, same). No bypass.
- **Guard 2** — `SandboxResolver::invocation` semantics are
  explicit: `Disabled` → `Ok(None)` (passthrough by design),
  `Auto` + no backend → `Ok(None)` (silent passthrough — the
  caller is expected to warn via `has_any`), `Require` + no
  backend → `Err(SandboxViolation)` naming the install command.
  Refuse-on-Require, not fall-through.
- **Guard 6** — `kill_child_tree` (tools.rs:241-256) sends
  `SIGKILL` to the process group (`kill(-pgid, ...)`), with the
  child spawned under `process_group(0)` (tools.rs:1194) and
  `setsid(2)` (tools.rs:1201) so grandchildren are reachable.
  `check.rs:437-440` mirrors the same pattern.

## Audit findings: kod-core-serve (0 changes, all candidates refuted)

Audited `serve.rs` (1940 lines), `acp.rs` (1408), `transport.rs`
(278). Six guards scanned; two candidates surfaced, both refuted
by reading the call path.

### R1 — peer-UID check — SAFE

`transport.rs:134-175`: `accept()` calls `check_stream_peer(&s)?`
**before** the split (`s.into_split()`), where `peer_cred()` is
still reachable. `check_stream_peer` compares `cred.uid()` to
`current_uid()` and returns `PermissionDenied` on mismatch.

`serve.rs:182-208` calls `listener.accept()` and, on `Ok(stream)`,
spawns `handle_connection`. There is no way to reach
`handle_connection` with an unverified peer — the check is at the
transport layer, not a helper the caller must remember to invoke.
Same shape as the `ReadFileTool` tool-layer guarantee from the
`conflict_handler` audit: the guard is where the socket is, not
where the caller is.

### R2 — NDJSON line cap — SAFE

The dispatch reader uses `CappedLines` (`serve.rs:303-390`) with
`MAX_REQUEST_LINE_BYTES = 1 MiB` (`serve.rs:387`). The cap is
enforced *during* `fill_buf` — a pre-fix bug (`M-19`) read with
`BufReader::lines()` and no bound, and the current code checks
`buf.len() + content_take > self.cap` inside the read loop, so a
newline-less stream aborts at the cap rather than after allocating.

ACP is separately capped at `MAX_FRAME_BYTES = 16 MiB`
(`acp.rs:70`), checked at `acp.rs:938`.

Both protocols have a byte-bounded reader.

### Other guards checked and clean

- **Version negotiation** — `serve.rs:449` rejects any `v` outside
  `MIN_PROTOCOL_VERSION..=MAX_PROTOCOL_VERSION`. The hello handler
  also emits a range-based `compatible` flag (`:487-495`) so a
  client that speaks a future version is told the mismatch. ACP
  has its own `PROTOCOL_VERSION = 1` check at `acp.rs:379-383`.
- **Panic isolation** — `serve.rs:203-208` awaits the handler's
  `JoinHandle` and logs an `ERROR` on `Err(join_err)`, so a
  panicking connection task is visible in the logs and the accept
  loop survives. The provider-panic path (a panic inside the
  engine, not the handler) has its own error-frame tests
  (`panic_guard_tests`).
- **Request-id echo** — every `write_ok` / `write_error` /
  `write_ack` passes `&req.id`. A malformed request (JSON parse
  failure) writes `id: ""`, the documented sentinel for
  "unparseable" so the client knows not to expect a correlated
  reply on a real id.
- **Single instance** — `transport::bind` (`transport.rs:74`)
  runs check-then-bind under an exclusive `flock` to prevent two
  daemons racing on a stale socket. `transport_bind_replaces_a_stale_socket_file`
  and `prepare_socket_refuses_when_a_live_listener_exists`
  test both branches.
