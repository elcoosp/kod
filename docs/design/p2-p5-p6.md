# Design: P2 meta-attention, P5 swarm briefs, P6 background jobs

Status: draft · Covers the three multi-week items from the harness
review. P2 and P6 are new subsystems; P5's types exist and need
integration. Each section below defines the interface, the
integration points, the test strategy, and the open questions that
must be resolved before implementation.

---

## P2 — Meta-attention context engine

### Problem

Today the transcript is a recency FIFO: 40 turns, 4k chars per turn,
oldest dropped. Pinned turns, the decisions log, and the plan survive
by construction. Nothing scores individual chunks against the
current query — a tool call from 30 turns ago that is exactly the
call site the current prompt needs is dropped as eagerly as a
"thanks" from 5 turns ago.

The doc's proposal: re-score every chunk against the current query
and render each at one of four fidelities — Omit, Stub, Digest,
Full.

### Why kod is close

- `reallocate_with_jev` already reweights section budgets per query.
- Memory entries are individually Jev-filtered.
- `ChatMessage` carries `id`, `role`, `tool_calls`, and
  `MessageMetadata { pinned, token_count, .. }`.
- The `retrieval.rs` scorer (BM25-lite + vector + recency) already
  exists and is used for long-term memory.
- The `budget.rs` allocation already treats history as one section
  with a char cap.

What is missing is the same treatment one level down: a score per
`ChatMessage`, and a fidelity decision from that score.

### Data model

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum Fidelity { Omit, Stub, Digest, Full }

#[derive(Clone)]
pub struct ContextChunk<'a> {
    /// Borrowed from the transcript. The chunk never owns the
    /// message; the renderer clones only what it keeps.
    pub message: &'a ChatMessage,
    /// Turn index (position in the transcript, newest = 0).
    pub age_turns: u32,
    /// Lazy digest. Computed once per chunk per turn if Digest or
    /// Stub is chosen; never computed if Full or Omit.
    pub digest: Option<String>,
}
```

### Interface

```rust
pub trait ChunkScorer: Send + Sync {
    /// Score a chunk against the current query. Returns the fidelity
    /// at which the renderer should emit it.
    fn score(&self, chunk: &ContextChunk<'_>, query: &Query) -> Fidelity;
}
```

Two implementations:

**`LexicalScorer`** — the deterministic default. No model call.
Scoring rule (mirrors `retrieval.rs`):

- Pinned → Full.
- A tool error result in the last N turns → Stub at minimum
  (error legibility is a correctness concern).
- Term overlap with the query, weighted by inverse document
  frequency: `score = Σ ln(total / df(term))` for each distinct
  query term the chunk contains.
- Recency: `recency = exp2(-age_turns / half_life)` with
  `half_life = 64`.
- Combined: `combined = 0.7 * overlap + 0.3 * recency`.
- Thresholds: `> 2.5 → Full`, `> 1.2 → Digest`, `> 0.4 → Stub`,
  else Omit.

**`JevScorer`** — wraps `LexicalScorer`. After the lexical pass,
chunks scored Stub or Digest (the boundary cases) are batched into
one Jev call: "For each of these N chunks, does the current query
need it in full, as a summary, or not at all?" Fail-open: a Jev
error falls back to the lexical score. Batching keeps the cost at
one Jev round-trip per turn, not one per chunk.

### Integration points

- `engine::render_history_for(key)` (engine/mod.rs) is the single
  call site that produces the history string. It becomes:
  1. Clone the transcript into `Vec<ContextChunk>`.
  2. Score each chunk.
  3. Render by fidelity:
     - Omit → nothing.
     - Stub → the first line (role prefix + 80 chars).
     - Digest → the digest string (2-3 sentences).
     - Full → the current `render_text()` output.
  4. Join into the history string.

- The `PromptBudget`'s history share still caps total chars. The
  scorer decides *which* chunks survive; the budget decides the
  total size.

- **Cache-neutral by construction**: the fidelity decisions change
  per turn (they depend on the query), so the transcript string is
  volatile. That is already true today — the transcript is not in
  the cacheable prefix. The cacheable prefix is the system prompt
  up to the volatile marker; the transcript is under
  `## Conversation so far`, which is volatile.

### Test strategy

1. Unit tests on `LexicalScorer` with a synthetic chunk set and a
   fixed query: the pinned chunk is Full, the error chunk is Stub,
   the off-topic chunk is Omit.
2. A golden test: a fixed transcript + query produces a fixed
   rendered history string. The `characterization_prompts` suite
   already does this shape for the whole prompt; a new scenario
   `snapshot_meta_attention_history` pins the history subsection.
3. A property test: total rendered length is monotonic in the
   fidelity threshold — raising the threshold never increases
   rendered size.
4. A fail-open test: a `JevScorer` wrapping a client that always
   errors produces the same output as `LexicalScorer` alone.

### Open questions

- **Digest computation.** Where does the 2-3 sentence summary come
  from? Options: (a) a Jev call per chunk, (b) a cheap extractive
  summary (first sentence + last sentence), (c) a separate small
  model. The doc implies (a); the design recommends (b) as the
  default with (a) as an opt-in, because a Jev call per chunk per
  turn is expensive.
- **Cache-aware transposition.** If the fidelity of the *most
  recent* turn changes between two calls, the transcript changes
  and Anthropic's transcript cache breakpoint loses. The design
  should pin the fidelity of the last K turns (K = 5, say) to Full
  so the growing edge of the transcript is stable. This is a P0/P2
  interaction worth calling out.
- **Interaction with `/pin`.** A pinned message is always Full;
  this is a feature, not a bug. But a user who pins 100 messages
  has effectively disabled the feature. The design should cap the
  pinned count or warn at some threshold.

## P5 — Swarm brief wiring

### Problem

The types exist (`ContextBrief`, `SubagentReport`, `assemble_brief`,
`merge_report`). What does not exist is the plumbing from the
engine's state into the swarm runner's per-subtask loop, and from
the subagent's response back into the engine's decisions log and
steers queue.

### Interface

The runner currently builds a subagent prompt like:

```rust
let shaped = format!("{role_prefix}{}", subtask.description);
```

It becomes:

```rust
let brief = assemble_brief(
    &subtask.description,
    &role_prefix,
    capability_constraints(subtask.capability),
    &parent_context,
);
let shaped = render_brief(&brief);
```

`render_brief` is a new function that renders a `ContextBrief` into
a text prompt. It is the inverse of nothing — the brief is a struct,
not a parseable format — so it renders freely:

```
## Goal
<goal>

## Constraints
- <constraint>
- ...

## Relevant decisions
- <decision>
- ...

## Files you may touch
- <path>: <summary> (<lines> lines)
- ...

## Repo map slice
<repomap>

## Write scope
Your writes must stay within: <globs>
```

### Parent context construction

`SwarmRunner::run()` needs a `ParentContext`. It is built once
before the dispatch loop from the engine's state:

```rust
async fn build_parent_context(engine: &KodEngine, subtasks: &[Subtask]) -> ParentContext {
    let decisions = engine.recent_decisions().await; // new method
    let repomap = engine.repomap_text().await;
    let expected_writes: Vec<String> = subtasks
        .iter()
        .flat_map(|s| s.expected_writes.iter().cloned())
        .collect();
    // File summaries: for each path mentioned in any subtask's
    // description or expected_writes, read the first few lines.
    let file_summaries = summarize_relevant_files(engine, subtasks).await;
    ParentContext { decisions, file_summaries, repomap_text: repomap,
                    expected_writes, token_budget: 4096 }
}
```

The `recent_decisions` method is new: it reads the engine's
decision log for the default transcript key and returns the last
N decisions as strings.

### Report merging

When an agent completes, its text output is passed back. Today it
is appended to the concatenated result. Under P5:

- The agent is asked (via the brief's constraints) to return a
  JSON `SubagentReport`.
- The runner parses it. A response that does not parse falls back
  to a `SubagentReport { summary: text, ..Default::default() }`
  and logs a warning — the subagent's prose is never lost.
- `merge_report(&report, &brief)` produces a `MergePlan`.
- The runner applies the plan:
  - `decisions_to_record` → `engine.record_decision(text).await`
  - `steers_to_queue` → `engine.steer(text).await` (deferred to
    the parent's next turn)
  - `boundary_violations` → a `SwarmEvent::BoundaryViolation` event
    the TUI surfaces
  - `summary_line` → concatenated into the run's output, replacing
    the full text.

### Test strategy

1. A unit test on `render_brief` with a fully-populated brief: all
   sections present in the expected order.
2. A unit test on the report parser: a valid JSON report parses;
   a prose response becomes a fallback report.
3. An integration test in `swarm_runner.rs` with a stub engine:
   the parent's decisions appear in the rendered prompt; a report
   with a boundary violation produces the event.

### Open questions

- **Brief token budget.** The `ParentContext::token_budget` field
  is carried but nothing enforces it. The design should specify
  the truncation rule: truncate `relevant_decisions` first, then
  `file_digests`, then `repomap_slice`. The goal and constraints
  are never truncated.
- **Report parsing reliability.** Asking the model for JSON is a
  known-fragile pattern. The design should include a lenient
  parser: strip markdown fences, accept a bare summary if no JSON
  block is found.

## P6 — Background read-only jobs

### Problem

Cross-model review, background evals, and docs generation are
extensions of the normal workflow that run alongside it. kod has
fragments: REVIEWER/RESEARCHER role preambles, per-capability
endpoint routing, a blackboard, and steers as a delivery channel.
What is missing is a runner that makes "background" a first-class,
enforced state rather than a prompt-level suggestion.

### Interface

```rust
pub struct BackgroundJobRunner {
    jobs: DashMap<JobId, JobState>,
    sem: Arc<Semaphore>,   // cap concurrent background agents
}

pub enum JobKind {
    /// Cross-model review of a completed turn.
    Review { subject: TurnId, endpoint: ModelRef },
    /// An eval run against a recorded transcript.
    Eval { transcript: PathBuf },
    /// Generate prose documentation for a module.
    Docs { path: PathBuf },
}

pub struct JobState {
    kind: JobKind,
    started_at: Instant,
    status: JobStatus,
}

pub enum JobStatus {
    Running,
    Completed { summary: String },
    Failed { error: String },
}
```

### Read-only enforcement

The design's core safety property: a background job **cannot**
mutate the workspace. This is enforced at the tool layer, not by a
prompt:

1. The child engine is created with `preset = read-only`.
2. The tool registry is filtered to a whitelist: `read_file`,
   `grep`, `search_files`, `file_info`, `git_status`, `git_diff`,
   `lsp`, `check`. No `write_file`, no `patch_file`, no
   `execute_command`, no `git_commit`.
3. The child's `ToolContext` has `write_files: false` and
   `execute_commands: false` regardless of the preset — belt and
   braces.

If a background job asks for a tool that is not on the whitelist,
the tool call fails with a `PolicyDenied` result and the job logs
the attempt. A job that tries to write has a bug; failing closed
is the correct response.

### Cross-model review

The REVIEWER role uses a different endpoint than the one that
produced the turn. The design picks the endpoint by:

1. The turn's recorded endpoint (from `SessionEntry::Cost`).
2. Any endpoint in `routing.swarm` whose capability is `CodeReview`
   and whose name differs.
3. Fallback: the same endpoint, with a warning ("cross-model review
   unavailable; running same-model").

### Results

A job's output lands in three places:

1. The blackboard (`kod_swarm::blackboard`), keyed by job id.
2. A `System` message on the TUI if the job's summary is short.
3. Optionally, a steer on the parent's next turn if the job
   produced actionable notes. Off by default; a config flag
   enables it.

### TUI surface

A `/jobs` command lists running and recently-completed jobs with
their status. A `/jobs attach <id>` streams a running job's
progress. The design specifies the surface but not the full
implementation — a minimal `/jobs` list is the first pass.

### Test strategy

1. A unit test on the tool whitelist: a registry filtered for a
   background engine has exactly the whitelisted tools.
2. A unit test on the concurrency cap: a runner with `sem = 1`
   serializes two jobs.
3. An integration test with a stub engine: a job that tries to
   write fails, a job that reads succeeds.
4. A test on the endpoint picker: three cases (turn endpoint,
   routing.swarm, fallback).

### Open questions

- **Lifecycle.** When does a background job's result become
  visible? The design's answer: immediately on the blackboard, and
  on the next turn as a steer if enabled. A user who never looks
  at `/jobs` sees the steer note.
- **Resource limits.** A background job consumes an endpoint
  connection. If the main session is mid-turn on the same
  endpoint, the job queues behind it. The design should cap the
  number of background jobs and document the interaction with the
  P1 circuit breaker.

## Sequencing

The three items are independent but share a test-discipline
requirement: each lands behind a feature flag (`[meta_attention]
enabled`, `[swarm] typed_briefs`, `[background] enabled`) so a
regression can be bisected by turning one off.

1. **P5 wiring** first — smallest surface, the types exist, and the
   integration is mechanical once `ParentContext` is built.
2. **P6** second — new module, no existing behavior to migrate.
3. **P2** last — the largest, and the one whose behavior change is
   most visible in a golden prompt.

Each item gets its own commit series. A partial landing (types but
not wiring) is explicitly allowed; the feature flags make "off" the
default until the wiring is complete.

## Status as of this session

A short record of what is real and what is a stub, so the next
session does not have to reverse-engineer the state from the commit
log.

### P2 — not started

Design only. The `ChunkScorer` trait, the `LexicalScorer`, and the
fidelity rendering are all unimplemented. Open questions from § P2
still need answers:

- Digest source (extractive default vs. Jev vs. separate model)
- Pin the last K turns to Full to keep the transcript cache
  breakpoint stable (a P0/P2 interaction)
- Pinned-count warning threshold

### P5 — complete

Real:
- `ContextBrief`, `SubagentReport`, `assemble_brief`, `merge_report`,
  `render_brief`, `parse_report`, `boundary_violations`
- The swarm runner builds a `ParentContext` before the wave loop and
  renders a brief per subtask via `render_brief`. Subagents receive a
  structured prompt with the parent's decisions, file digests, the
  repomap slice, the write-scope globs, and an explicit
  response-format instruction.
- The completion arm parses the subagent's reply with `parse_report`,
  builds a `MergePlan` with `merge_report`, and applies it:
  decisions to the parent's decisions log, open questions to the
  steers queue, boundary violations to a `SwarmEvent::BoundaryViolation`,
  the summary to the blackboard.

Note: the routing is unit-tested in `brief_assembly`; it is not
exercised end-to-end by an integration test that runs a real swarm
with a real subagent. A future test could drive `SwarmRunner::run`
against a stub engine and assert the decisions log gained an entry.

### P6 — runner and enforcement are real, review is a stub

Real:
- `BackgroundJobRunner` (DashMap + semaphore + retention prune)
- `READ_ONLY_TOOLS` whitelist, enforced at `KodEngine::run_tool`
  when the engine's `background_mode` flag is set
- `enable_background_mode` / `is_background`
- `/jobs` and `/review` TUI commands
- The engine holds one runner; `spawn_background_review` allocates
  an id, picks an alternative endpoint (or falls back with a
  warning), registers the job, and completes it

Not implemented:
- `spawn_background_review`'s task completes with a placeholder
  summary. It does not construct a child `KodEngine`, does not
  install the read-only tool registry, and does not call
  `process_for` with a review preamble. No cross-model review runs.

To finish: a `KodEngine::new_background_child(...)` constructor that
takes a `RouterConfig` derived from the parent, marks
`background_mode = true`, filters the registry to `READ_ONLY_TOOLS`,
and returns an `Arc<KodEngine>`. Then `spawn_background_review`
builds the child, calls `child.process_for("review", &prompt).await`,
and completes the job with the reply's summary. The result should
also land on the swarm blackboard keyed by job id.

### P3 — tool is real, integration is deferred

Real:
- `ToolSearchTool`, inventory behind `Arc<RwLock<ToolInventory>>`,
  engine registration, `refresh_tool_inventory`
- Five tests

Deferred:
- The per-turn Jev category filter (`filter_tool_definitions_with_jev`)
  still runs — now under P0 hysteresis. The plan was for
  `tool_search` to make it unnecessary. That replacement is a
  separate decision: it changes what tools are present in the
  default request, which affects the golden-prompt snapshots.

### P4 — loader and router integration are real

Real:
- `InstructionChain`, `parse_agents_md`, `When`, guard matching,
  root-to-leaf shadowing
- Router renders sections into the volatile prompt before the
  conversation transcript. `path=` guards evaluate against the
  input's @-references; `task=` against the classified task type.
- Nine tests

Note: the `lang=` guard evaluates against an empty language list
today (the router does not have repomap file stats in scope at
`build_prompt_with_budget`). A section guarded only on `lang=rust`
never fires. The design called this out as a "future pass"; it
remains future.
